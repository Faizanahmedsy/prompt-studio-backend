# Putting it online for nothing — Render + Neon

The API on [Render](https://render.com)'s free plan, the database on
[Neon](https://neon.com)'s. No card on either, no trial clock, nothing to
cancel later.

**The trade:** a free Render service sleeps after 15 minutes with no traffic,
and the next request waits about a minute while it wakes. Everything else
behaves normally. If that is acceptable, this is the least work of any option
by a distance — no server to patch, no TLS to renew, no backups to script.

**Not Render's Postgres.** Render's free database is **deleted 30 days after
it is created**. Neon's free plan has no expiry. Use Neon.

---

## 1 · The database

1. Sign up at [neon.com](https://neon.com) — GitHub login, no card.
2. Create a project. Name it `prompt-studio`, region **AWS US East 2 (Ohio)**.
   That is the region this blueprint puts Render in, and every query crosses
   the gap between the two — so put them in the same place.
3. On the dashboard, copy the connection string. It looks like:

   ```
   postgresql://neondb_owner:PASSWORD@ep-cool-sun-a1b2c3.us-east-2.aws.neon.tech/neondb?sslmode=require&channel_binding=require
   ```

   Take the **direct** connection, not the pooled one. Both work, but the
   pooled endpoint is pgBouncer in transaction mode, which quietly breaks
   asyncpg's prepared statements — and we do our own pooling anyway.

Paste it exactly as it is. `?sslmode=require&channel_binding=require` are
libpq's words, not asyncpg's, and passing them through untouched raises
`TypeError: connect() got an unexpected keyword argument 'sslmode'` at the
first query. `app/core/config.py` translates the whole string on the way in, so
what the dashboard gives you is what you paste.

## 2 · The API

1. Sign up at [render.com](https://render.com) with GitHub and give it access
   to `prompt-studio-backend`.
2. **Blueprints → New Blueprint Instance**, pick the repo, branch `main`. It
   reads [`render.yaml`](../render.yaml) and creates the service already
   configured.

   > The branch matters more than it looks. The existing service was created
   > from the dashboard pointing at `feat/backend` while every sprint merged
   > into `main`, so a finished sprint deployed nothing and the repo gave no
   > clue why. `render.yaml` now states `branch: main`, but a service created
   > by hand does not read that file — for that one, change it under
   > **Settings → Build & Deploy → Branch**.
3. It will ask for the four values the file marks `sync: false`:

   | | |
   |---|---|
   | `DATABASE_URL_OVERRIDE` | the Neon string from step 1 |
   | `BACKEND_CORS_ORIGINS` | `["https://prompt-studio-nu.vercel.app"]` |
   | `SUPERADMIN_EMAIL` | your address — this is the first login |
   | `SUPERADMIN_PASSWORD` | something long; change it after signing in |

   `SECRET_KEY` is generated by Render and never shown. Leave it alone: changing
   it signs every account out.

4. Deploy. The first build takes 5–10 minutes — it is building the image from
   scratch. Watch the log for `[start] migrating`, then `[start] serving`.

You get a URL like `https://prompt-studio-api.onrender.com`. Check it:

```bash
curl https://prompt-studio-api.onrender.com/health
```

Expect `{"success": true, ..., "data": {"status": "ok", ...}}`. The first call
after a sleep takes about a minute — that is the free plan, not a fault.

## 3 · Point the frontend at it

In the Vercel project for `prompt-studio`, set:

```
NEXT_PUBLIC_API_URL=https://prompt-studio-api.onrender.com
NEXT_PUBLIC_WS_URL=wss://prompt-studio-api.onrender.com
```

`wss://`, not `ws://` — the page is served over HTTPS and a browser refuses a
plain-text socket from a secure page, silently enough that collaboration simply
never connects. Redeploy the frontend; environment variables are baked in at
build time.

Then make sure the Vercel URL is in `BACKEND_CORS_ORIGINS` on Render, or every
request fails preflight with no useful error in the UI.

## What you are actually getting

| | Free allowance | What runs out first |
|---|---|---|
| Render web service | 750 instance-hours/month | sleeps at 15 min idle; ~1 min to wake |
| Neon Postgres | 0.5 GB storage, 100 compute-hours/month | suspends at 5 min idle |

One always-on service would use ~730 of the 750 hours, so the sleeping is what
keeps you inside the allowance rather than a limit you fight.

**Neon suspending is handled.** `pool_pre_ping` in `app/core/database.py` tests
a pooled connection before handing it out, so the first query after a wake
re-opens rather than failing on a dead socket.

**Collaboration still works,** on one worker. There is no Redis here, and there
does not need to be: Redis exists so that browsers on *different* workers hear
each other, and `scripts/start.sh` runs exactly one. `app/core/redis.py`
degrades to in-process fan-out on its own. If you ever add a second worker, add
Redis in the same breath — two workers without it means two people on one
project silently not seeing each other's edits.

**WebSockets keep the service awake.** Render counts messages on an open socket
as traffic, so an active session does not sleep underneath the people using it.
Only the first visitor after a quiet spell waits.

## When to stop using this

The free plan is right for showing the thing to people. It is the wrong shape
for anyone depending on it, for one reason: **there is no backup**. Neon's free
plan has no point-in-time restore. Before this matters to anybody, take a dump
somewhere on a schedule:

```bash
pg_dump "$NEON_URL" | gzip > "backup-$(date +%F).sql.gz"
```

The upgrade path when the sleeping stops being funny is Render Starter at
$7/month — same service, same config, no sleep.
